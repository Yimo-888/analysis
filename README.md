# Demo — Inventory Intelligence & Dynamic Pricing Engine

A self-contained demo of a **data-driven inventory analytics, product-lifecycle,
and dynamic-pricing engine** for a catalog of perishable goods (stock ages,
eventually passes its shelf life, and is priced off a per-unit cost). Every day it
ranks the whole catalog, classifies each SKU, decides what to reorder vs. clear out
vs. write off, computes clearance discounts, and bulk-posts marketplace listings.

> 🔗 **Live demo:** _add your deploy URL here_
> ⚙️ Built with Django + SQLite + Chart.js. All data is **synthetic** (generated by
> a seed command); there are no external integrations and no secrets.

---

## Why this exists

This is a clean-room reimplementation of design ideas I developed for a production
inventory system, rebuilt from scratch over synthetic data so it can be shown
publicly. The interesting part isn't the CRUD — it's the **decision engine** and a
real **v1 → v2 design evolution**: the first version was elegant inventory theory
that broke on messy operational data, and the second is the version worth shipping.

---

## Four apps, one site

It's structured as a multi-app Django site (mirroring the real system): a shared
`core` data layer plus four independent feature apps you can open and read on
their own.

| App | URL | What it is |
|---|---|---|
| **Analytics (v1)** | `/analytics/` | The original, textbook design — classical inventory metrics (weighted demand, **safety stock, reorder point, EOQ, inventory turnover**) and a **Pareto-optimal frontier**. Stat cards, Top-by-Profit / Top-by-ROI charts, a product table with Optimal/Optimize status, and a per-product **detail modal** (sales-trend, inventory levels, performance radar). Includes a v1-vs-v2 note showing where it breaks. |
| **DX Analytics (v2)** | `/dx-analytics/` | The production rewrite: grounded sell-through, catalog ranking, an **8-way category cascade**, plus a filterable catalog table and per-SKU detail pages. |
| **Automation** | `/automation/` | **One-click listing posting** — processes the whole catalog in one run: each base SKU is exploded into variant listings (variant type × pack size), generated, and posted in bulk **batch jobs** with per-item status tracking (posted / pending / failed) and a pipeline-flow view. |
| **Lifecycle** | `/lifecycle/` | A 6-tier **state machine** (NEW → STAR → CORE → WATCH → LIQUIDATE → DISPOSE) and the **clearance-discount** queue with a per-SKU factor breakdown. |

The home page (`/`) introduces all four and explains how the pipeline connects them.

## The engine (the actual content)

**1. Per-SKU metrics** — from one year of daily sales, over recency-weighted
windows (0–60 / 61–180 / 181–365 days):

```
weighted_daily_sales = 0.5·recent + 0.3·mid + 0.2·long      (daily rates)
sell_through_rate    = units_sold / (avg_inventory + units_sold)   # bounded, "grounded"
velocity             = units_sold / days_with_a_sale
days_of_inventory    = current_inventory / weighted_daily_sales
roi                  = (tier_price − unit_cost) / unit_cost
portfolio_score      = 0.4·norm(velocity) + 0.3·norm(sell_through) + 0.3·norm(roi)
```

**2. Categorization cascade** (priority order, using portfolio-wide percentiles):

```
rank > boundary (challenged):  high capital at risk → Liquidate Candidate, else Dispose Candidate
otherwise (healthy):
  new & above-median            → New High Performer
  out of stock & no recent sale → Slow Mover/Watch     (freeze, don't liquidate)
  top-quartile STR & good ROI   → High-Demand Rare Item
  on the Pareto frontier        → Core Portfolio
  in stock but slow & low STR   → Slow Mover
  else                          → Standard
```

**3. Lifecycle routing** — categories map to a 6-tier state machine
(`NEW · STAR · CORE · WATCH · LIQUIDATE · DISPOSE`); challenged SKUs are routed by
**where the stock physically sits** (aging open stock vs. sealed stock vs.
nothing), and stock past its shelf life is written off.

**4. Dynamic clearance discount** (website liquidations only):

```
discount % = 10 + 0.30·rank_factor + 0.30·age_factor + 0.40·overstock_factor
             clamped to 5–40%
```

**5. Automated listing posting** — fan each base product out into a fixed grid of
variant listings (variant type × pack size), generate each listing's SKU and title,
and post them in bulk batch jobs, tracking every item as posted / pending / failed.

## Design evolution: v1 → v2

| | **v1 — idealized** | **v2 — production** |
|---|---|---|
| Sell-through | `units ÷ current stock` → explodes when nearly OOS | `units ÷ average stock` → bounded, honest |
| Out-of-stock SKUs | still scored as healthy | routed to *Slow Mover/Watch* and frozen |
| Output | Pareto-optimal / not + a score | 8-way category cascade → lifecycle tier → price action |
| Scale | per-SKU queries | bulk-loaded, ~constant query count for the whole catalog |
| Missing cost | assumed clean | fallbacks + guards (no crashes on zero cost) |

The **Analytics (v1)** app demonstrates this with planted SKUs — e.g.
`DEMO-PHANTOM` is out of stock with a little stale history: v1's snapshot-based
sell-through makes it look like a star, while v2 grounds the signal in average
inventory and correctly freezes it.

## Run it locally (3 commands)

```bash
python -m venv venv && source venv/bin/activate && pip install -r requirements.txt
python manage.py migrate
python manage.py seed_demo          # synthetic catalog + sales + analytics
python manage.py runserver          # → http://127.0.0.1:8000
```

Run the test suite:

```bash
python manage.py test
```

## Deploy

A `render.yaml` is included for one-click deploy on [Render](https://render.com)'s
free tier (`build.sh` installs, collects static files, migrates, and seeds). A
`Procfile` is provided for Railway / Heroku-style platforms. Set `DEBUG=0` and a
real `SECRET_KEY` in the environment.

## Tech stack

- **Django 4.2** (engine, ORM, templating) · **SQLite** · **gunicorn** + **WhiteNoise**
- **Chart.js** + **Bootstrap 5** (via CDN) for the dashboards
- Pure-Python statistics (no heavy numeric deps) — easy to read and deploy

## Project layout

```
core/                        shared data + orchestration
  models.py                  Product · DailySale · AnalyticsResult
  services/
    metrics.py               per-SKU base metrics + numeric helpers
    pricing.py               cost → tier → price map (illustrative; drives ROI)
    run.py                   the pipeline: core → analytics → dx_analytics → lifecycle
  management/commands/        seed_demo · run_analytics
  tests.py                   per-app logic tests + a full view smoke test
analytics/   models.py + services.py   v1: classical inventory metrics + Pareto frontier
dx_analytics/services.py     v2: grounded sell-through, ranking, category cascade
lifecycle/services.py        tier routing + clearance-discount engine
automation/   models.py + services.py   PostingJob/Listing + the variant fan-out
<each app>/views.py, urls.py     its own pages, mounted under its own URL prefix
templates/<app>/             Bootstrap pages per app
```

Each feature app is presentation + domain logic over the shared `core` data, so
each one can be shown and explained independently.

### Note

The catalog uses **generic SKUs** (`SKU-0001`, `Product 0001`, `Vendor 07`) and every
sales, inventory, cost, pricing, and listing number is **fabricated** by the seed
command. Nothing is drawn from any real catalog or company data — the point is to
showcase the engineering and the design reasoning.
